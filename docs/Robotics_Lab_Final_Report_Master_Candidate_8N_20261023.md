**專題定位：** 基於 Python 與 PyBullet 之人形機器人動作控制模擬

**參考方向：** Alpha 1S 人形機器人動作控制概念

**實作模型：** PyBullet `humanoid/humanoid.urdf`

**研究範圍：** 固定基座模型、Action Frame、關節角度控制、Smoothstep 動作插值及 GUI 模擬驗證

## 第一章　研究動機

### 1.1 研究背景

隨著機器人技術的發展，人形機器人（Humanoid Robot）逐漸成為機器人教育、運動控制與人機互動的重要學習對象。人形機器人具有模仿人體結構的關節配置，能透過多個關節的協調控制，執行舉手、彎肘及其他姿態變化。

在人形機器人的動作控制中，除了理解關節結構與旋轉方向之外，也必須掌握關節角度、動作順序及時間控制等基本概念。透過設定不同的目標姿態，並控制各姿態之間的轉換過程，可以將原本獨立的關節操作整合為連續動作。

然而，直接使用實體機器人進行實驗，通常需要具備相容的硬體設備、控制軟體與操作環境。因此，本專題選擇 Python 程式語言與 PyBullet 物理模擬平台，作為學習人形機器人動作控制的實作工具。

本專題參考《Alpha 1S 人形機器人之動作控制與程式設計》專題報告範例所呈現的人形機器人動作控制方向 [2]，將動作拆分、關節角度設定及時間控制等概念，轉化為 Python 與 PyBullet 模擬程式的設計基礎。

### 1.2 研究動機與目的

本專題的研究動機，在於透過可實際執行的程式與三維模擬環境，建立對人形機器人動作控制原理的理解，並將關節角度設定、動作影格與時間控制整合為完整的實作流程。

相較於僅從教材理解機器人關節與致動器的工作方式，透過 PyBullet 模擬可以直接觀察不同控制命令對機器人姿態的影響，並利用程式輸出比對目標角度與實際角度，進一步分析關節控制結果。

本專題的具體目的如下：

1. 建立 Python 與 PyBullet 人形機器人模擬環境，並確認模型可正常載入與操作。
2. 分析 PyBullet 人形模型的關節結構、關節型態及旋轉自由度。
3. 建立 16 個邏輯控制欄位，完成與實際 URDF 關節的靜態映射。
4. 利用 Action Frame 定義初始姿態、抬手姿態及簡化揮手動作。
5. 使用 Smoothstep 插值方法，實現多個動作影格之間的連續姿態轉換。
6. 透過關節角度紀錄及 GUI 模擬影片，驗證動作執行結果並整理實驗證據。

透過上述實作，本專題希望建立從模型結構分析、關節控制、動作設計到模擬驗證的基礎學習流程。

### 1.3 專題研究範圍與限制

本專題以 Python 與 PyBullet 為主要實作工具，研究對象為 PyBullet 提供的 `humanoid/humanoid.urdf` 人形模型。實驗採用固定基座（Fixed Base）設定，主要觀察上肢關節的動作控制結果。

本專題已實作四個 Action Frames，分別為初始姿態、抬右手、彎曲右手肘及重新伸直右手肘。各影格之間使用 Smoothstep 方法進行角度插值，並透過 PyBullet GUI 呈現連續動作。

在關節映射方面，本專題建立 16 個邏輯控制欄位，對應模型中 12 個不同的可活動關節，並以 PyBullet DIRECT 模式完成 Joint ID、Joint Name 與 Joint Type 的靜態一致性驗證。

本專題的研究限制如下：

1. 使用的是 PyBullet 範例人形模型，並非 Alpha 1S 實體機器人。
2. 模型採固定基座設定，不進行自主站立、平衡控制或步行實驗。
3. 主要動態控制成果集中於右肩膀與右手肘，未對全部 16 個邏輯控制欄位進行逐項動態驗證。
4. 揮手動作採用簡化的彎肘與伸肘往返控制，不代表已重現真實人形機器人的完整揮手動作。
5. 關節控制誤差主要根據指定保持時間結束後的量測結果分析，尚未進行整段動作的完整動態誤差評估。

因此，本專題的成果定位為**人形機器人關節與動作控制的模擬實作及概念驗證**，不延伸宣稱實體機器人的運動控制性能。

## 第二章　Alpha 1S 與人形機器人結構

### 2.1 Alpha 1S 人形機器人概述

Alpha 1S 為一款以人形結構與動作控制為特色的機器人，具有頭部、軀幹、雙手臂及雙腿等主要構造，可作為學習機器人關節動作與程式控制概念的參考對象。透過多個關節的協調控制，人形機器人可以依照預先設定的動作順序，呈現不同姿態及連續動作。

在人形機器人的動作設計中，關節角度與動作時間是兩項重要參數。操作者可以將一個完整動作拆分為數個動作影格（Action Frame），分別設定各影格的目標姿態，再依照指定時間執行影格之間的轉換。例如，一個簡化的揮手動作可以分成初始姿態、抬起手臂、彎曲手肘及伸直手肘等階段。

本專題參考《Alpha 1S 人形機器人之動作控制與程式設計》專題報告範例所呈現的人形機器人動作控制方向 [2]，將動作拆分、關節角度設定及時間控制等概念，轉化為 Python 與 PyBullet 模擬程式的設計基礎。

需要說明的是，本專題並未直接使用 Alpha 1S 實體機器人，也未實作其原廠控制通訊協定。實際實驗採用 PyBullet 提供的 `humanoid/humanoid.urdf` 人形模型。因此，本專題所設計的 16 個邏輯控制欄位，是針對 PyBullet 模型建立的軟體層控制介面，不等同於 Alpha 1S 原廠伺服馬達的配置或控制編號。

透過上述區分，本專題將 Alpha 1S 作為人形機器人動作控制的概念參考，而以 PyBullet 模擬模型作為實際驗證對象，藉此探討關節結構、動作影格與連續姿態控制的基本原理。

### 2.2 人形機器人的關節與伺服馬達

人形機器人的運動主要依靠關節（Joint）與致動器（Actuator）相互配合。關節負責描述機器人各部位之間允許的相對運動方式，而致動器則提供驅動關節所需的力量或扭矩。這些概念亦屬於機器人基本結構與控制原理的學習範圍 [1]。以人形機器人的手臂為例，肩關節可用於調整手臂方向，肘關節則可用於執行彎曲與伸展動作。

在實體機器人中，伺服馬達（Servo Motor）是常見的關節致動方式之一。伺服控制系統可根據目標位置及回授資訊調整馬達輸出，使關節逐漸接近指定角度。然而，關節與伺服馬達並不是完全相同的概念：關節描述機械結構與運動限制，伺服馬達則屬於驅動裝置。

在機器人模擬環境中，關節通常透過模型描述檔定義。本專題使用的 URDF（Unified Robot Description Format）檔案，記錄模型的連桿（Link）、關節名稱、關節類型及連接關係。PyBullet 讀取 URDF 後，便可依照模型的關節特性執行動作控制。

本專題使用的 PyBullet 人形模型主要包含以下三種關節類型：

1. **球形關節（Spherical Joint）：** 可描述三維空間中的旋轉運動，適合用於具有多個旋轉自由度的部位，例如肩膀與髖部。
2. **旋轉關節（Revolute Joint）：** 允許關節沿單一旋轉軸運動，例如本專題模型中的肘部與膝部。
3. **固定關節（Fixed Joint）：** 不允許相連部位產生相對運動，例如模型中的部分固定連接位置。

自由度（Degree of Freedom, DOF）表示系統可獨立運動的變數數量。以本專題使用的模型為例，球形關節具有三個旋轉自由度，而旋轉關節具有一個旋轉自由度。不過，實際控制方式仍須依照 PyBullet 的關節類型及相關 API 設定。

本專題在程式中建立 16 個邏輯控制欄位，用於表示希望觀察或控制的關節運動方向。由於部分欄位對應同一個球形關節，因此 16 個邏輯控制欄位並不代表模型具有 16 個不同的活動關節，也不代表配置了 16 顆實體伺服馬達。

在已完成的實驗中，本專題主要針對右肩膀球形關節與右手肘旋轉關節進行動態控制，透過指定目標角度與動作時間，呈現抬手、彎肘及伸肘等連續姿態。其他邏輯控制欄位則已完成與 URDF 關節資訊的靜態映射驗證，尚未全部進行獨立動態控制測試。

因此，本專題的關節控制應理解為**透過 PyBullet 模擬控制器驅動虛擬模型的關節運動**，而非直接向 Alpha 1S 實體伺服馬達傳送控制命令。透過這種模擬方式，可以先理解關節結構、自由度與目標角度控制之間的關係，作為後續研究人形機器人動作控制的基礎。

### 2.3 PyBullet 人形模型結構

PyBullet 為一套可透過 Python 操作的物理模擬工具，能用於剛體運動、關節控制及機器人動作模擬 [4]、[5]。本專題採用 PyBullet 範例資料中的 `humanoid/humanoid.urdf`，作為人形機器人關節控制的主要實驗模型。

URDF（Unified Robot Description Format）以連桿（Link）及關節（Joint）描述機器人的結構。連桿代表機器人的身體部件，關節則定義相鄰連桿之間的連接與運動方式。PyBullet 可載入 URDF 模型並提供關節資訊查詢與控制功能 [5]。本專題使用此功能建立具備軀幹、頭部、雙手臂與雙腿的人形模擬模型。

本專題曾使用 PyBullet 的 `getNumJoints()` 與 `getJointInfo()` 函式檢查模型關節資訊，確認模型共有 15 個關節項目，其中包含 8 個球形關節（Spherical Joint）、4 個旋轉關節（Revolute Joint）及 3 個固定關節（Fixed Joint）。

各類關節分布如下：

| 關節類型 | 數量 | 對應部位 |
|---|---:|---|
| Spherical Joint | 8 | 胸部、頸部、左右肩膀、左右髖部、左右腳踝 |
| Revolute Joint | 4 | 左右手肘、左右膝蓋 |
| Fixed Joint | 3 | root、左右手腕 |
| **合計** | **15** | **完整 URDF 關節項目** |

其中，球形關節可描述三個旋轉自由度，而旋轉關節具有一個旋轉自由度。因此，以模型關節類型進行計算，8 個球形關節與 4 個旋轉關節合計提供 28 個關節旋轉自由度。固定關節不增加可獨立控制的旋轉自由度。

需要注意的是，關節旋轉自由度數量、URDF 關節數量及本專題自行設計的邏輯控制欄位數量，分別代表不同概念，不應直接視為相同數值。

本專題主要使用的關節資訊如下：

| Joint ID | Joint Name | Joint Type | 本專題用途 |
|---|---|---|---|
| 3 | `right_shoulder` | Spherical | 右肩膀 Z 軸舉手 |
| 4 | `right_elbow` | Revolute | 右手肘彎曲與伸直 |

由於 `right_shoulder` 為球形關節，在 PyBullet 中可以使用 Quaternion（四元數）表示其旋轉姿態。本專題先以 Euler Angle（歐拉角）定義目標姿態，再利用 PyBullet 提供的轉換函式，將其轉換成控制所需的 Quaternion。

相較之下，`right_elbow` 為單軸旋轉關節，可使用單一目標角度描述其彎曲或伸直姿態。透過這兩種關節的控制，本專題得以組合出抬手、彎肘及伸肘等動作影格。

在模擬設定上，本專題使用固定基座（`useFixedBase=True`），並將模型放置於指定的空間位置與方向。固定基座設定能減少整體模型位移對上肢關節觀察的干擾，使實驗集中於指定關節的姿態變化。

因此，本專題的 PyBullet 模型主要用於關節結構分析及固定基座下的動作控制驗證，而非自主平衡、實際站立或行走控制。

上述 URDF 結構也作為下一節「2.4 16 個邏輯控制欄位與 URDF 關節映射」的依據，以說明軟體控制欄位如何對應至模型中的實際關節項目。

### 2.4 16 個邏輯控制欄位與 URDF 關節映射

為了建立較容易理解的人形機器人關節控制介面，本專題以 Python 設計 16 個邏輯控制欄位（Logical Control Fields），分別表示軀幹、頸部、雙手臂及雙腿的部分旋轉方向與關節動作。

本專題使用 `src/humanoid_joint_mapping.py` 儲存控制欄位的對應資料，記錄每個欄位的邏輯編號、名稱、URDF Joint ID、Joint Name、Joint Type 及所代表的旋轉方向。

需要特別說明的是，邏輯控制欄位屬於本專題自行定義的軟體抽象介面，並不是 PyBullet 模型原生提供的 16 個獨立關節，也不是 Alpha 1S 實體機器人的伺服馬達編號。

#### 2.4.2 邏輯欄位與關節數量之關係

本專題建立的 16 個邏輯欄位，實際對應至 12 個不同的可活動 URDF 關節。

例如，`right_shoulder_x` 與 `right_shoulder_z` 都對應 Joint ID 3，也就是 `right_shoulder` 球形關節。兩個欄位表示同一關節的不同旋轉方向，而不是兩個獨立的肩部關節。

因此，本專題須區分以下三種數量：

1. **15 個 URDF 關節項目：** 模型原始關節清單，包含固定關節。
2. **12 個不同的可活動關節：** 本專題 16 個邏輯控制欄位所涵蓋的關節。
3. **16 個邏輯控制欄位：** 本專題自行設計的軟體映射欄位。

此外，模型中的可活動關節合計具有 28 個旋轉自由度；16 個邏輯控制欄位並未涵蓋全部旋轉自由度。

#### 2.4.3 URDF 靜態映射驗證

為確認邏輯控制欄位與 PyBullet 模型的一致性，本專題使用 PyBullet DIRECT 模式載入 `humanoid/humanoid.urdf`，並透過 `getNumJoints()` 與 `getJointInfo()` 取得模型關節資訊。

驗證內容包括：

1. 邏輯欄位總數是否為 16 個。
2. 邏輯編號是否連續且沒有重複名稱。
3. 每個 Joint ID 是否位於模型有效範圍。
4. Joint Name 是否與 PyBullet 讀取的實際名稱一致。
5. Joint Type 是否與實際關節類型一致。
6. 映射結果是否涵蓋 12 個不同的可活動關節。

依據已執行的 PowerShell 與 PyBullet 驗證紀錄，16 個邏輯控制欄位全部通過靜態一致性檢查，程式輸出包含：

```text
Validated Logical Fields: 16
Unique Physical Model Joints: 12
=== Mapping Validation PASS ===
Python Exit Code: 0
```

此處輸出中的 `Physical Model Joints` 是驗證程式對模型關節的統計名稱，指的是 URDF 中不同的模型關節，並非 12 個實際安裝的馬達。

上述測試確認了控制欄位與模型關節資訊的靜態對應關係，但不能直接推論 16 個欄位皆已完成動態控制或角度追蹤測試。

#### 2.4.4 本專題的實際控制範圍

在目前已完成的動作控制實驗中，主要使用兩個關節：

- `right_shoulder`：以局部 Z 軸方向的旋轉設定，執行約 0° 至 +45° 的抬手動作。
- `right_elbow`：以單軸目標角度設定，執行約 0° 至 30° 的彎肘與伸肘動作。

上述兩個關節透過 Action Frame 與 Smoothstep 動作插值進行連續姿態控制，並已建立 GUI 模擬影片及角度誤差紀錄。

其餘邏輯控制欄位目前主要完成靜態映射與模型資訊核對，未全部實施獨立的動態控制實驗。

綜合而言，本專題已建立一套具備 16 個邏輯控制欄位的 PyBullet 人形模型映射資料，並完成其靜態一致性驗證。這項成果可作為後續擴充關節控制功能的基礎，同時保留目前實驗範圍與驗證程度之間的明確界線。

## 第三章　動作控制原理

### 3.1 Action Frame 動作影格設計

動作影格（Action Frame）是一種以離散目標姿態描述機器人動作的方法。透過將完整動作拆分為多個具有順序的目標姿態，控制程式可以依序調整指定關節，形成連續動作。此概念與動畫製作中的關鍵影格（Keyframe）相似，各影格記錄重要姿態，而影格之間的過渡則由插值方法計算。

本專題使用 Python 建立 `src/humanoid_action_frames.py`，集中管理各動作影格的關節角度與時間參數。動作影格資料主要包含影格編號、動作名稱、右肩膀旋轉姿態、右手肘目標角度、動作持續時間及終點保持時間等資訊。

#### 3.1.1 動作影格資料設計

本專題以 Euler Angle（歐拉角）描述右肩膀的局部旋轉姿態，並以單一角度描述右手肘的彎曲或伸直。時間控制則區分為動作持續時間（Duration）與終點保持時間（Hold Time）。

其中，Duration 表示由前一姿態過渡至目標姿態所設定的模擬時間；Hold Time 則表示到達該影格目標姿態後，額外維持控制命令的模擬時間。

這些參數是程式設定的名義模擬時間，不代表已經量測或保證實際執行時的牆上時鐘時間（Wall-clock Time）。

#### 3.1.2 四個動作影格之設定

本專題已建立四個動作影格，如下表所示：

| Frame | 動作名稱 | 右肩膀 Euler Angle [X, Y, Z] | 右手肘角度 | Duration | Hold Time |
|---|---|---|---|---|---|
| 01 | Initial Pose | [0°, 0°, 0°] | 0° | 2.0 s | 0.5 s |
| 02 | Raise Right Arm | [0°, 0°, 45°] | 0° | 2.0 s | 0.5 s |
| 03 | Wave Right Arm - Bend | [0°, 0°, 45°] | 30° | 1.0 s | 0.3 s |
| 04 | Wave Right Arm - Extend | [0°, 0°, 45°] | 0° | 1.0 s | 0.3 s |

Frame 01 為初始姿態，右肩膀及右手肘均設定為零度。Frame 02 將右肩膀局部 Z 軸設定為正 45 度，呈現抬手姿態。Frame 03 在維持右肩膀姿態的情況下，將右手肘設定為 30 度。Frame 04 再將右手肘恢復至零度，形成簡化的彎肘與伸肘往返動作。

上述動作僅涉及右肩膀及右手肘的指定控制，並非完整人體揮手運動的重現。

#### 3.1.3 動作影格執行流程

本專題的四影格 GUI 控制器依照以下順序執行：

**Initial Pose → Raise Right Arm → Wave Right Arm - Bend → Wave Right Arm - Extend**

控制程式先設定模型初始姿態，再逐一讀取後續影格的目標角度及時間參數。各影格之間採用 Smoothstep 插值，使目標姿態隨模擬步數逐漸變化。

需要注意的是，Frame 01 雖然在資料檔案中具有 Duration 及 Hold Time 欄位，但目前四影格 GUI 程式主要將其用於初始化姿態；程式啟動時的初始等待流程，不等同於完整播放 Frame 01 所宣告的動作持續時間與保持時間。

因此，本專題的實際連續控制重點為 Frame 01 至 Frame 02、Frame 02 至 Frame 03，以及 Frame 03 至 Frame 04 的姿態轉換。

#### 3.1.4 動作影格設計的應用與限制

使用 Action Frame 的優點是可以將關節目標姿態與執行控制流程分開管理。當需要調整動作幅度或速度時，可以修改影格中的角度或時間參數，再由控制程式套用相應設定。

本專題已透過 PyBullet GUI 完成四個影格的姿態呈現，並針對主要控制關節建立目標角度、實際角度與誤差紀錄。

不過，Action Frame 本身只是目標姿態的資料定義；機器人是否準確到達目標角度，仍受到模擬控制器、控制參數及模擬步進方式影響。因此，不能僅憑影格資料存在，就認定關節動作已完成驗證。

綜合而言，本專題以四個 Action Frames 建立簡化的右手臂動作序列，作為後續研究關節自由度、旋轉姿態表示、Smoothstep 插值與時間控制的實作基礎。

### 3.2 關節角度與自由度

關節角度（Joint Angle）與自由度（Degree of Freedom, DOF）是機器人動作控制的重要基礎。關節角度用於描述關節沿指定方向的旋轉量，而自由度則表示關節或機械系統可以獨立運動的變數數量。透過理解兩者之間的關係，才能正確設定機器人的目標姿態及控制方式。

#### 3.2.1 關節角度與目標姿態

在人形機器人的關節控制中，程式可以指定某個關節的目標角度，再由控制器使其逐步接近指定姿態。

例如，本專題將右手肘的目標角度由 0° 設定為 30°，用於模擬彎肘動作；之後再將目標角度設定回 0°，形成伸肘動作。

關節角度與控制命令並非完全相同的概念。目標角度表示控制器希望關節到達的位置，而實際角度則是模擬模型在特定時間所呈現的關節狀態。

因此，若要評估關節控制結果，應同時記錄目標角度與實際角度，並比較兩者之間的差異。

本專題使用絕對角度誤差（Absolute Angular Error）作為部分關節追蹤結果的檢查方式，其計算如下：

\[
e_{\theta} = \left|\theta_{\mathrm{target}}-\theta_{\mathrm{actual}}\right|
\]

其中，\(\theta_{\mathrm{target}}\) 表示目標角度，\(\theta_{\mathrm{actual}}\) 表示實際角度，\(e_{\theta}\) 則表示兩者的絕對差值。

此公式適用於本專題所記錄的單軸角度或指定姿態比較結果；若涉及任意三維旋轉姿態，則須注意角度表示方式及旋轉差異的計算方法。

#### 3.2.2 關節自由度的基本概念

自由度表示一個系統可獨立運動的參數數量。不同關節類型具有不同的自由度特性。

本專題使用的 PyBullet 人形模型包含三種主要關節類型：

| 關節類型 | 旋轉自由度 | 動作特性 | 模型範例 |
|---|---:|---|---|
| Spherical Joint | 3 | 可描述三維旋轉姿態 | `right_shoulder` |
| Revolute Joint | 1 | 沿指定軸旋轉 | `right_elbow` |
| Fixed Joint | 0 | 不允許相對運動 | `right_wrist` |

球形關節的三個旋轉自由度可用於描述複雜的空間姿態，但這不代表其內部一定裝有三顆實體馬達。

以右肩膀為例，本專題透過 Euler Angle 設定局部 Z 軸方向的旋轉量，並使用 Quaternion 作為 PyBullet 控制球形關節時的姿態表示。

右手肘則屬於單軸旋轉關節，因此可以使用一個目標角度設定其彎曲或伸直狀態。

#### 3.2.3 本專題模型的自由度統計

經由 PyBullet 關節資訊檢查，本專題使用的 `humanoid/humanoid.urdf` 模型包含 15 個關節項目，其中有 8 個球形關節、4 個旋轉關節及 3 個固定關節。

由於每個球形關節具有 3 個旋轉自由度，每個旋轉關節具有 1 個旋轉自由度，因此模型的關節旋轉自由度總數為：

\[
DOF_{\mathrm{joint}} = 8\times3+4\times1=28
\]

此數值僅表示模型可活動關節的旋轉自由度總和，並未計入自由浮動基座的運動自由度。本專題採用固定基座設定，也沒有研究整體模型的自由移動或平衡控制。

另外，本專題建立的 16 個邏輯控制欄位，只是針對部分關節方向所設計的軟體映射介面，不等同於 28 個旋轉自由度，也不是 16 個獨立馬達。

#### 3.2.4 本專題的關節角度控制範圍

目前已完成的連續動作模擬，主要涉及右肩膀與右手肘兩個關節。

| 關節 | Joint ID | 類型 | 實驗中的目標設定 |
|---|---:|---|---|
| `right_shoulder` | 3 | Spherical | 局部 Z 軸 0° → +45° |
| `right_elbow` | 4 | Revolute | 0° → 30° → 0° |

右肩膀的局部 Z 軸角度設定，用於呈現抬手姿態；右手肘的角度變化則用於呈現彎肘與伸肘往返動作。

需要注意的是，以上是本專題設定的目標角度，不代表關節在所有模擬步數中都與目標值完全一致。實際角度可能因控制器運作、模擬步進及姿態保持過程而產生差異。

本專題已在部分動作影格到達終點並完成保持時間後，記錄目標角度、實際角度及其誤差，作為控制結果的驗證資料。

綜合而言，理解關節角度與自由度，可以協助區分模型結構、目標姿態及控制結果。這也是本專題後續使用 Euler Angle、Quaternion 及 Smoothstep 插值方法設計連續動作的基礎。

### 3.3 Euler Angle 與 Quaternion

在三維空間中，機器人的關節姿態可以使用不同的數學方法表示。其中，歐拉角（Euler Angle）與四元數（Quaternion）是常見的旋轉姿態表示方式。本專題透過歐拉角定義右肩膀的目標旋轉姿態，再轉換為四元數，作為 PyBullet 球形關節控制器的目標輸入。

#### 3.3.1 Euler Angle 歐拉角

歐拉角是一種使用三個旋轉參數描述三維姿態的方法。常見的表示方式包括繞 X、Y、Z 軸的旋轉角度，但實際旋轉結果會受到座標系統與旋轉順序影響。

本專題將右肩膀的目標姿態以三個角度值儲存在 Action Frame 中，例如：

| 動作影格 | 右肩膀 Euler Angle [X, Y, Z] | 說明 |
|---|---|---|
| Frame 01 | [0°, 0°, 0°] | 初始姿態 |
| Frame 02 | [0°, 0°, 45°] | 右肩局部 Z 軸正向旋轉 |
| Frame 03 | [0°, 0°, 45°] | 維持右肩姿態 |
| Frame 04 | [0°, 0°, 45°] | 維持右肩姿態 |

這種表示方式容易閱讀，適合用來設定動作影格的目標姿態。

不過，歐拉角並非沒有缺點。當不同旋轉軸的轉動組合在一起時，旋轉順序會影響最後姿態；在部分特殊姿態下，也可能出現萬向節鎖（Gimbal Lock）問題，使旋轉參數的表示產生退化。

因此，歐拉角適合用於本專題的動作目標設定，但在三維旋轉控制中仍需要正確處理其姿態轉換。

#### 3.3.2 Quaternion 四元數

四元數是一種可用四個數值表示三維旋轉姿態的數學工具。PyBullet 使用四元數表示球形關節的旋轉姿態，其常見資料形式為：

`[x, y, z, w]`

四元數的四個分量不應直接理解成繞 X、Y、Z 軸的三個角度再加上一個額外角度。

對於有效的單位四元數，其分量需要滿足：

\[
x^2+y^2+z^2+w^2=1
\]

相較於直接以歐拉角進行複合旋轉運算，四元數能避免歐拉角表示法的萬向節鎖問題，並適合用於三維姿態的運算與插值。

需要注意的是，使用四元數並不代表機器人控制器一定沒有追蹤誤差，也不代表所有姿態轉換都會自動變得平滑。

#### 3.3.3 本專題的 Euler Angle 至 Quaternion 轉換

本專題在 Action Frame 中以角度為單位記錄右肩膀的目標姿態，但 PyBullet 的 `getQuaternionFromEuler()` 函式所接收的 Euler Angle 參數使用弧度（Radian），相關姿態轉換方式可參考 PyBullet 技術文件 [5]。

因此，控制程式需要先將角度轉換成弧度，再進行四元數轉換。

角度與弧度之間的換算關係為：

\[
\theta_{\mathrm{rad}}=\theta_{\mathrm{deg}}\times\frac{\pi}{180}
\]

以右肩膀局部 Z 軸正向旋轉 45° 為例，其弧度為：

\[
45^\circ\times\frac{\pi}{180}=\frac{\pi}{4}
\]

對應的 Python 概念示範如下：

```python
import math
import pybullet as p

shoulder_euler_deg = [0, 0, 45]

shoulder_euler_rad = [
    math.radians(angle)
    for angle in shoulder_euler_deg
]

shoulder_quaternion = p.getQuaternionFromEuler(
    shoulder_euler_rad
)
```

上述程式示範了本專題使用的角度轉換概念。`shoulder_quaternion` 可作為球形關節目標姿態的表示資料，但實際關節控制還需要配合 PyBullet 的馬達控制 API、控制參數及模擬步進。

#### 3.3.4 Euler Angle 與 Quaternion 在本專題中的角色

本專題使用歐拉角與四元數的目的不同：

1. **Euler Angle：** 用於在 Action Frame 中定義容易理解的右肩膀目標姿態。
2. **Quaternion：** 用於將三維旋轉姿態轉換成 PyBullet 球形關節控制器可接收的資料形式。
3. **Joint State：** 用於取得模擬中的實際關節狀態，以便與目標姿態進行比較。

其中，右手肘屬於 Revolute Joint，主要以單一旋轉角度控制，不需要像球形肩關節一樣，以完整四元數表示其目標旋轉姿態。

本專題的右肩膀動態控制主要採用局部 Z 軸的 0° 至 +45° 姿態變化，並未對全部三維旋轉組合進行獨立控制測試。

因此，本專題已驗證的是特定右肩膀旋轉設定下的模擬動作，而不是所有歐拉角與四元數姿態組合的完整控制性能。

綜合而言，歐拉角提供了直觀的關節目標設定方式，四元數則提供適合三維旋轉控制的姿態表示方法。兩者結合，使本專題能夠將 Action Frame 中的角度資料轉換為 PyBullet 球形關節控制器所需的目標姿態，作為後續 Smoothstep 動作插值與連續姿態控制的基礎。

### 3.4 Smoothstep 動作插值

在機器人動作控制中，若直接將關節目標角度由一個數值切換至另一個數值，控制器可能收到不連續的目標位置命令。因此，在動作影格之間加入插值（Interpolation）方法，可以讓目標姿態隨時間逐漸變化，使動作呈現較平順的過渡效果。

本專題採用 Smoothstep 插值方法，計算前一動作影格與下一動作影格之間的目標姿態。此方法主要用於產生連續的目標角度命令，而非直接保證模擬關節一定能完全追蹤該命令。

#### 3.4.1 線性插值的基本概念

線性插值（Linear Interpolation）是一種依照進度比例，計算起始值與結束值之間數值的方法。

假設關節起始角度為 \(\theta_0\)，目標角度為 \(\theta_1\)，而 \(u\) 表示介於 0 與 1 之間的正規化動作進度，則線性插值可表示為：

\[
\theta(u)=\theta_0+(\theta_1-\theta_0)u
\]

當 \(u=0\) 時，角度等於起始值；當 \(u=1\) 時，角度等於目標值。

以右手肘由 0° 彎曲至 30° 為例，當動作進度為 50% 時，線性插值的目標角度為：

\[
\theta(0.5)=0+(30-0)\times0.5=15^\circ
\]

線性插值容易實作，但在動作開始與結束的邊界位置，其目標角速度可能突然改變，因此本專題進一步使用 Smoothstep 方法調整插值進度。

#### 3.4.2 Smoothstep 插值函數

Smoothstep 是一種三次多項式插值函數，可將正規化進度轉換為平滑的插值比例，其數學形式如下：

\[
s(u)=3u^2-2u^3,\qquad 0\leq u\leq1
\]

其中，\(u\) 為正規化動作進度，\(s(u)\) 為 Smoothstep 輸出的插值比例。

Smoothstep 具有以下性質：

\[
s(0)=0,\qquad s(1)=1
\]

\[
s'(0)=0,\qquad s'(1)=0
\]

這表示插值函數在起點及終點的斜率為零。在設定的動作持續時間固定時，所產生的目標角度軌跡可以在起點與終點具有零目標角速度。

不過，這不代表實際關節速度、加速度或控制誤差必然為零；實際運動結果仍取決於模擬控制器與物理步進。

#### 3.4.3 關節目標角度的計算

本專題將 Smoothstep 插值比例代入起始角度與目標角度之間的計算式：

\[
\theta(u)=\theta_0+(\theta_1-\theta_0)s(u)
\]

其中：

- \(\theta_0\)：起始角度。
- \(\theta_1\)：目標角度。
- \(u\)：正規化動作進度。
- \(s(u)\)：Smoothstep 插值比例。
- \(\theta(u)\)：目前進度對應的目標角度。

以右手肘由 0° 彎曲至 30° 為例：

| 正規化進度 | Smoothstep 比例 | 目標角度 |
|---|---:|---:|
| 0% | 0.000 | 0.00° |
| 25% | 0.15625 | 4.6875° |
| 50% | 0.500 | 15.00° |
| 75% | 0.84375 | 25.3125° |
| 100% | 1.000 | 30.00° |

由上述結果可知，Smoothstep 的目標角度在開始與結束階段變化較慢，中間階段則變化較快。

上述數值為數學函數計算結果，不是從 PyBullet 實際關節狀態取得的測量值。

#### 3.4.4 本專題的 Python 實作概念

本專題的 GUI 動作控制程式依照動作持續時間與模擬步數，逐步產生插值進度，再計算對應的關節目標姿態。

Smoothstep 的 Python 概念程式如下：

```python
def smoothstep(u):
    u = max(0.0, min(1.0, u))
    return 3 * u**2 - 2 * u**3

def interpolate_angle(start_deg, target_deg, progress):
    ratio = smoothstep(progress)
    return start_deg + (target_deg - start_deg) * ratio

elbow_target = interpolate_angle(
    start_deg=0.0,
    target_deg=30.0,
    progress=0.5
)

print(elbow_target)  # 15.0
```

以上程式用於說明 Smoothstep 的插值原理，不代表完整的 PyBullet GUI 控制程式。

在實際動作流程中，本專題以 240 Hz 的模擬步進設定，依照各影格的 Duration 產生逐步變化的目標角度。對右肩膀球形關節，則將插值後的歐拉角姿態轉換為 Quaternion，再交由 PyBullet 控制器使用。

本專題的已驗證動作主要沿右肩膀局部 Z 軸變化，尚未將此方法擴充驗證至任意三維旋轉姿態。一般三維旋轉插值須考慮旋轉順序與姿態表示方式，不能直接假定逐項歐拉角插值等同於四元數球面線性插值（SLERP）。

#### 3.4.5 Smoothstep 在四影格動作中的應用

本專題使用 Smoothstep 進行以下三段姿態轉換：

| 動作轉換 | 主要角度變化 | Duration | Hold Time |
|---|---|---:|---:|
| Frame 01 → 02 | 右肩 Z 軸 0° → 45° | 2.0 s | 0.5 s |
| Frame 02 → 03 | 右手肘 0° → 30° | 1.0 s | 0.3 s |
| Frame 03 → 04 | 右手肘 30° → 0° | 1.0 s | 0.3 s |

Duration 表示過渡所設定的名義模擬時間；Hold Time 表示到達目標姿態後持續施加目標控制命令的名義模擬時間。

Frame 01 主要用於初始姿態設定，因此不將其資料欄位中的 Duration 與 Hold Time 直接計入上述三段正式過渡的時間。

在各段動作中，Smoothstep 提供逐步變化的目標姿態；PyBullet 控制器則負責使虛擬關節接近這些目標值。本專題另以終點及保持階段的角度紀錄檢查追蹤結果。

綜合而言，Smoothstep 能夠改善動作影格之間的目標角度過渡方式，使本專題的抬手、彎肘與伸肘動作具備連續的目標姿態變化。不過，其實際效果仍須搭配關節狀態測量及 GUI 模擬結果判斷，不能僅依數學插值函數就宣稱已完全消除運動誤差。

### 3.5 關節控制與時間設定

在人形機器人的動作控制中，除了設定目標關節姿態之外，也需要決定控制命令的更新方式、動作持續時間及姿態保持時間。本專題透過 PyBullet 關節控制 API、Smoothstep 插值與固定模擬步進，建立四個 Action Frames 的連續姿態控制流程。

#### 3.5.1 關節位置控制

本專題主要採用位置控制（Position Control）方式，向 PyBullet 模擬關節指定目標姿態，再透過物理模擬步進，使模型關節逐漸接近目標值。PyBullet 提供 `setJointMotorControlMultiDof()` 與 `setJointMotorControl2()` 等關節控制 API，可依關節類型設定相應的控制命令 [5]。

由於不同關節類型的姿態表示方式不同，本專題分別處理右肩膀與右手肘：

| 關節 | Joint ID | 關節類型 | 控制方式 |
|---|---:|---|---|
| `right_shoulder` | 3 | Spherical | `setJointMotorControlMultiDof()`，使用 Quaternion 目標姿態 |
| `right_elbow` | 4 | Revolute | `setJointMotorControl2()`，使用單一目標角度 |

其中，右肩膀球形關節的目標姿態先由 Euler Angle 轉換成 Quaternion，再交由多自由度關節控制 API 處理。

右手肘則使用單軸位置控制，指定 0°、30° 或插值過程中的中間目標角度。

上述控制方式是對 PyBullet 虛擬關節施加控制命令，不涉及 Alpha 1S 實體伺服馬達的通訊或驅動。

#### 3.5.2 模擬步進與時間換算

本專題使用每秒 240 個模擬步進（240 Hz）作為動作控制的時間基準，其對應的模擬時間間隔為：

\[
\Delta t=\frac{1}{240}\text{ s}
\]

當某段動作設定的持續時間為 \(T\) 秒時，可依模擬頻率計算相應步數：

\[
N=T\times240
\]

例如，Duration 設定為 2.0 秒，對應 480 個模擬步進；Duration 設定為 1.0 秒，則對應 240 個模擬步進。

動作控制程式可根據目前步數與總步數計算正規化進度，接著透過 Smoothstep 函數產生各步的目標姿態。

需要注意的是，240 Hz 代表本專題設定的模擬步進基準，並不代表 Windows 電腦畫面的實際更新率，也不保證程式每秒一定完成 240 次物理運算。

#### 3.5.3 Duration 與 Hold Time

本專題將動作時間分成兩個部分：

1. **Duration：** 由目前姿態過渡至下一目標姿態的名義模擬時間。
2. **Hold Time：** 動作過渡完成後，持續維持目標控制命令的名義模擬時間。

已完成的三段正式動作轉換設定如下：

| 動作轉換 | Duration | Hold Time | 名義模擬時間合計 |
|---|---:|---:|---:|
| Frame 01 → 02 | 2.0 s | 0.5 s | 2.5 s |
| Frame 02 → 03 | 1.0 s | 0.3 s | 1.3 s |
| Frame 03 → 04 | 1.0 s | 0.3 s | 1.3 s |
| **合計** | **4.0 s** | **1.1 s** | **5.1 s** |

上述 5.1 秒為三段正式過渡及保持階段的名義模擬時間加總，不包含模型載入、GUI 初始化、Frame 01 初始等待及其他程式執行開銷。

因此，不能直接將 5.1 秒視為影片總長度或實際經過的牆上時鐘時間。

#### 3.5.4 關節狀態讀取與誤差驗證

為評估模擬控制結果，本專題在動作執行過程中的指定檢查點，讀取主要關節的實際姿態，並與目標姿態進行比較。

右手肘為單軸旋轉關節，可以直接比較目標角度與讀取的實際角度。

右肩膀則為球形關節，需要先依照既定的旋轉姿態表示方式取得對應角度，再針對本專題使用的局部 Z 軸旋轉設定進行比較。

本專題的主要量測結果如下：

| 動作階段 | 關節 | 目標角度 | After Hold 實際角度 | 絕對誤差 |
|---|---|---:|---:|---:|
| Frame 02 | 右肩膀 Z 軸 | 45° | 44.800512° | 0.199488° |
| Frame 03 | 右手肘 | 30° | 30.000085° | 0.000085° |
| Frame 04 | 右手肘 | 0° | 0.000000° | 0.000000° |

上述結果對應指定影格完成保持階段後的量測值，並非整段動作所有時間點的平均誤差或最大誤差。

詳細量測紀錄保存於 `docs/Joint_Control_Test_Record.md`，可用於後續專題實作與成果分析章節。

#### 3.5.5 關節控制與時間設定之限制

本專題透過 Duration、Hold Time 及模擬步進控制動作執行順序，並以 GUI 呈現抬手、彎肘與伸肘等連續姿態。

然而，名義模擬時間與實際執行時間仍有差異。電腦效能、GUI 更新、程式等待及物理模擬運算等因素，可能影響使用者實際觀察到的執行時間。

此外，關節到達目標姿態的準確程度，也受到控制器參數與物理模擬條件影響。即使使用 Smoothstep 產生連續目標軌跡，實際關節仍可能存在追蹤誤差。

本專題已完成指定動作影格的終點角度及保持階段驗證，但尚未進行完整的動態軌跡誤差分析、真實硬體控制或自主平衡實驗。

綜合而言，本專題整合 Action Frame、Smoothstep 插值、PyBullet 關節位置控制與模擬時間設定，建立了可執行的四影格人形機器人動作控制流程，作為後續實作說明與結果分析的基礎。

### 4.2 人形模型載入與初始化

在人形機器人動作控制實驗中，必須先建立模擬環境並正確載入模型，才能進一步取得關節資訊、設定目標姿態及執行連續動作。本專題透過 PyBullet 載入 `humanoid/humanoid.urdf`，並採用固定基座設定，使實驗集中於右肩膀及右手肘的動作控制。

#### 4.2.1 PyBullet 人形模型載入

本專題使用 PyBullet 提供的人形機器人範例模型 `humanoid/humanoid.urdf`，透過 Python 程式建立物理模擬環境。

URDF 模型包含各部位的連桿、關節及連接關係，載入後即可透過 PyBullet API 查詢關節資訊，並設定指定關節的控制目標。

本專題使用 PyBullet GUI 模式觀察三維模型與連續動作，並於關節映射驗證階段使用 DIRECT 模式執行不需要視覺化視窗的靜態檢查。

#### 4.2.2 基座位置與初始姿態

本專題已完成的動作模擬採用固定基座（Fixed Base）設定，主要參數如下：

| 設定項目 | 參數 |
|---|---|
| URDF 模型 | `humanoid/humanoid.urdf` |
| 基座位置（Base Position） | `[0, 0, 4]` |
| 基座初始 Euler Angle | `[π/2, 0, 0]` |
| 固定基座 | `useFixedBase=True` |

上述基座初始 Euler Angle 使用弧度表示，其中 π/2 相當於 90°。程式可將此旋轉設定轉換為 Quaternion，作為載入模型時的初始方向。

需要注意的是，基座姿態與關節姿態屬於不同的設定。基座姿態決定整個模型載入時的空間方向，而右肩膀、右手肘的目標角度則控制模型內部的關節相對運動。

本專題將模型放置於指定的三維空間位置，並以固定基座方式進行模擬。此設定並不代表機器人已經站立在地板上，也不代表模型具備自主平衡或步行能力。

#### 4.2.3 關節資訊查詢與控制對象

模型成功載入後，本專題使用 `getNumJoints()` 與 `getJointInfo()` 查詢 URDF 關節資訊。

本專題主要控制的關節如下：

| Joint ID | Joint Name | Joint Type | 實驗用途 |
|---|---|---|---|
| 3 | `right_shoulder` | Spherical | 右肩膀局部 Z 軸舉手 |
| 4 | `right_elbow` | Revolute | 右手肘彎曲與伸直 |

其中，`right_shoulder` 的目標姿態以 Quaternion 表示，`right_elbow` 則使用單一旋轉角度設定。

在正式執行動作影格以前，控制程式需要建立可供後續控制使用的初始關節姿態。對本專題的四影格動作而言，Frame 01 定義右肩膀及右手肘的零度目標姿態，作為後續抬手與彎肘動作的起點。

#### 4.2.4 模型初始化與動作執行流程

本專題的模型初始化與動作控制可整理為以下流程：

1. 建立 PyBullet 模擬連線。
2. 設定模型資料來源與模擬環境。
3. 載入 `humanoid/humanoid.urdf`，套用基座位置、初始方向及固定基座設定。

在已完成的四影格 GUI 實驗中，Frame 01 主要用於建立初始姿態。其後的三段正式轉換使用 Smoothstep 插值，並依照各影格的 Duration 與 Hold Time 產生關節控制命令。

本專題尚未將上述問題納入實驗，也沒有驗證模型在自由基座條件下的自主站立與動作穩定性。

#### 4.3.1 動作影格的資料組成

本專題的 Action Frame 主要包含以下資料：

| 資料項目 | 說明 |
|---|---|
| Frame 編號 | 表示動作影格的執行順序 |
| 動作名稱 | 描述該影格的目標動作 |
| 右肩膀 Euler Angle | 定義右肩膀的三維目標旋轉姿態 |
| 右手肘目標角度 | 定義右手肘的彎曲或伸直角度 |
| Duration | 由前一姿態過渡至目前目標姿態的名義模擬時間 |
| Hold Time | 到達目標姿態後持續維持控制命令的名義模擬時間 |

上述項目為本專題動作影格的概念資料欄位，不應直接視為 Python 程式中已核對的變數名稱或資料鍵值；實際程式結構仍以 `humanoid_action_frames.py` 原始碼為準。

#### 4.3.2 四個動作影格的資料設定

本專題已建立四個動作影格，分別用於初始姿態、右手臂舉起、右手肘彎曲及右手肘重新伸直。

| Frame | 動作名稱 | 右肩膀 Euler Angle | 右手肘角度 | Duration | Hold Time |
|---|---|---|---:|---:|---:|
| 01 | Initial Pose | [0°, 0°, 0°] | 0° | 2.0 s | 0.5 s |
| 02 | Raise Right Arm | [0°, 0°, 45°] | 0° | 2.0 s | 0.5 s |
| 03 | Wave Right Arm - Bend | [0°, 0°, 45°] | 30° | 1.0 s | 0.3 s |
| 04 | Wave Right Arm - Extend | [0°, 0°, 45°] | 0° | 1.0 s | 0.3 s |

Frame 01 定義初始目標姿態；Frame 02 將右肩膀局部 Z 軸目標角度設定為 45°，呈現抬手動作；Frame 03 將右手肘設定為 30°；Frame 04 則將右手肘目標角度恢復為 0°。

透過上述設定，本專題將簡化的右手臂動作拆分成四個可依序執行的目標姿態。

#### 4.3.3 Action Frame 與控制程式的關係

本專題的動作控制流程可區分為兩個部分。

第一部分是 Action Frame 資料定義，主要負責記錄各影格的關節目標姿態及時間參數。

第二部分是 PyBullet GUI 控制程式，主要負責讀取動作影格、產生插值後的目標角度、設定關節控制命令及執行模擬步進。

在已完成的四影格實驗中，控制程式以 Frame 01 作為初始姿態，再依序執行 Frame 02、Frame 03 及 Frame 04 的姿態轉換。

各段正式動作轉換使用 Smoothstep 插值，依照 Duration 產生逐步變化的目標姿態，並於過渡後依照 Hold Time 持續維持目標控制命令。

需要說明的是，Frame 01 雖然具有 Duration 及 Hold Time 資料，但目前 GUI 控制流程主要將其作為初始化姿態使用，並未依照資料欄位完整播放該影格的過渡與保持時間。

#### 4.3.4 Action Frame 的實作優點與限制

使用 Action Frame 管理動作資料的優點，在於可以將動作設計與關節控制流程分開。當需要修改抬手角度、彎肘角度或動作持續時間時，可以先調整對應影格設定，再由控制程式讀取使用。

此外，將完整動作拆分成多個影格，有助於逐段觀察關節姿態及檢查執行結果。本專題已透過 GUI 模擬及指定檢查點的關節角度紀錄，驗證主要控制關節的部分動作結果。

然而，Action Frame 資料本身僅表示預先設定的目標姿態，不代表模擬關節必然完全到達目標值。實際控制結果仍受到 PyBullet 控制器、模擬時間設定及關節動態響應影響。

此外，本專題目前僅對右肩膀與右手肘執行連續動作控制，並未將全部 16 個邏輯控制欄位整合成完整的全身動作序列。

綜合而言，本專題已利用四個 Action Frames 建立可供 PyBullet 控制程式讀取的目標姿態與時間設定，完成簡化右手臂動作的資料設計基礎，並為後續右肩膀舉手、三姿態連續動作及四影格往返控制提供一致的動作設定來源。

### 4.4 右肩膀 Z 軸舉手控制

本專題首先以右肩膀局部 Z 軸舉手動作作為人形機器人關節控制的基本實驗，藉由單一關節的目標姿態變化，驗證 PyBullet 球形關節控制方式及姿態轉換流程。

本實驗使用 `humanoid/humanoid.urdf` 中的 `right_shoulder` 關節（Joint ID 3），將初始目標姿態設定為零度，再將局部 Z 軸目標角度調整至正 45 度，觀察模型右手臂的姿態變化。

#### 4.4.1 實驗目的與控制對象

本實驗主要目的在於確認 Python 程式能否透過 PyBullet 控制指定的球形關節，並使右肩膀依照目標姿態執行抬手動作。

主要控制設定如下：

| 項目 | 設定 |
|---|---|
| 模擬模型 | `humanoid/humanoid.urdf` |
| 關節名稱 | `right_shoulder` |
| Joint ID | 3 |
| Joint Type | Spherical |
| 初始 Euler Angle | [0°, 0°, 0°] |
| 目標 Euler Angle | [0°, 0°, 45°] |
| 控制方向 | 右肩膀局部 Z 軸 |
| 基座設定 | Fixed Base |

上述 45° 表示本專題指定的關節局部旋轉目標，不應直接理解為手臂相對地面或世界座標系的絕對仰角。

#### 4.4.2 右肩膀姿態控制流程

右肩膀為球形關節，具有三個旋轉自由度，因此本專題使用 Euler Angle 描述其目標姿態，再轉換為 Quaternion 作為 PyBullet 控制輸入。

其控制流程主要包含：

1. 載入 PyBullet 人形模型，確認右肩膀 Joint ID 為 3。
2. 建立右肩膀的初始零度目標姿態。
3. 將右肩膀局部 Z 軸的目標角度設定為正 45°。
4. 將目標 Euler Angle 由角度轉換成弧度。
5. 使用 `getQuaternionFromEuler()` 取得對應的 Quaternion。
6. 透過 `setJointMotorControlMultiDof()` 將目標姿態傳送至模擬關節控制器。
7. 執行 PyBullet 模擬步進，觀察右肩膀及手臂姿態變化。

其中，Euler Angle 與 Quaternion 的轉換屬於姿態資料處理；實際關節是否到達指定位置，仍由模擬控制器及物理模擬結果決定。

#### 4.4.3 舉手動作的連續姿態設定

為避免右肩膀的目標姿態瞬間由 0° 切換為 45°，本專題於連續動作控制階段使用 Smoothstep 插值，使目標角度依照設定的動作進度逐步變化。

在四影格動作設定中，Frame 01 至 Frame 02 的主要控制參數如下：

| 項目 | 設定 |
|---|---|
| 起始姿態 | Frame 01：右肩膀 Z 軸 0° |
| 目標姿態 | Frame 02：右肩膀 Z 軸 45° |
| Duration | 2.0 s |
| Hold Time | 0.5 s |
| 模擬步進基準 | 240 Hz |
| 插值方法 | Smoothstep |

在這段姿態過渡中，控制程式依照模擬進度產生右肩膀的中間目標角度，再將各步的目標姿態轉換為 Quaternion，交由 PyBullet 球形關節控制器使用。

本節所描述的 Smoothstep 過渡設定，屬於後續整合的 Action Frame 連續控制流程；早期單關節舉手實驗與後續四影格控制，不應在未核對執行程式及紀錄前視為完全相同的實驗版本。

#### 4.4.4 關節角度量測與驗證結果

本專題已在後續四影格控制實驗中，記錄 Frame 02 完成保持階段後的右肩膀姿態，用於檢查其是否接近指定的 45° 目標。

既有量測紀錄如下：

| 絕對角度誤差 | 0.199488° |

上述絕對角度誤差由目標角度與實際角度的差值計算：

\[

\]

這項結果顯示，在該次指定檢查點的量測條件下，右肩膀姿態接近 45° 目標值。

需要注意的是，該數值為後續四影格控制實驗於保持階段結束後的量測結果，不能直接視為早期單關節舉手版本的獨立測試數據，也不能代表整段抬手軌跡的平均誤差或最大誤差。

#### 4.4.5 實驗結果與限制

透過右肩膀局部 Z 軸舉手控制，本專題確認可使用 PyBullet 對球形關節指定旋轉姿態，並透過 GUI 觀察模型右手臂的姿態變化。

後續結合 Action Frame 與 Smoothstep 的實驗，也建立了右肩膀由 0° 過渡至 45° 的連續目標姿態設定，並留下保持階段後的角度量測紀錄。

然而，本實驗僅針對右肩膀的特定旋轉方向進行控制，未驗證球形關節所有旋轉方向及任意三維姿態組合。

此外，實驗使用固定基座的虛擬人形模型，不涉及 Alpha 1S 實體伺服馬達控制，也未研究抬手動作對整體機器人平衡與重心的影響。

綜合而言，本專題以右肩膀 Z 軸舉手作為基本關節控制實驗，建立了 Euler Angle、Quaternion、PyBullet 球形關節控制及關節狀態驗證之間的實作關係，並為後續三姿態連續動作及四影格往返控制奠定基礎。

### 4.5 三姿勢連續動作

在完成右肩膀局部 Z 軸舉手的基本控制後，本專題進一步將右肩膀及右手肘兩個關節的目標姿態組合，建立由初始姿態、抬手姿態至彎肘姿態的三姿勢連續動作。

相較於單一關節控制，三姿勢動作需要依照預定順序讀取不同目標姿態，並在姿態之間逐步更新控制命令，因此可用於學習多個動作階段的整合與執行流程。

#### 4.5.1 三姿勢動作設計

本專題三姿勢動作的主要概念，包含以下三個階段：

| 姿態階段 | 動作名稱 | 右肩膀局部 Z 軸目標 | 右手肘目標 |
|---|---|---:|---:|
| 姿態 01 | Initial Pose | 0° | 0° |
| 姿態 02 | Raise Right Arm | 45° | 0° |
| 姿態 03 | Wave Right Arm - Bend | 45° | 30° |

第一個姿態為初始姿態，右肩膀與右手肘均設定為零度。第二個姿態將右肩膀的局部 Z 軸目標角度調整至正 45 度，呈現抬手動作。第三個姿態維持右肩膀的目標姿態，並將右手肘目標角度設定為 30 度，形成彎肘動作。

上述三個姿態描述的是預先設定的關節控制目標，不能直接視為各階段實際量測得到的關節角度。

#### 4.5.2 三姿勢連續控制流程

本專題以 Action Frame 的概念管理各姿態的目標角度，並透過 PyBullet GUI 控制程式依序執行姿態變化。

其控制流程可整理如下：

1. 載入 PyBullet 人形模型，建立固定基座模擬環境。
2. 設定右肩膀及右手肘的初始目標姿態。
3. 將右肩膀局部 Z 軸目標角度由 0° 調整至 45°。
4. 在維持右肩膀目標姿態的情況下，將右手肘目標角度由 0° 調整至 30°。
5. 執行模擬步進，透過 GUI 觀察不同階段的姿態變化。

由於右肩膀屬於球形關節，控制程式需要將其 Euler Angle 目標姿態轉換為 Quaternion；右手肘則可使用單一旋轉角度進行控制。

上述流程建立了不同關節控制命令按照指定順序執行的基礎。

#### 4.5.3 動作插值與時間控制

為使不同姿態之間的目標角度逐步變化，本專題於連續動作控制中使用 Smoothstep 插值方式，根據動作進度產生中間目標姿態。

依據後續整合的四影格 Action Frame 設定，前三個影格的主要時間參數如下：

| 動作過渡 | Duration | Hold Time |
|---|---:|---:|
| Frame 01 → 02 | 2.0 s | 0.5 s |
| Frame 02 → 03 | 1.0 s | 0.3 s |

上述參數為後續四影格資料中前兩段正式過渡的設定，可作為理解三姿勢動作控制邏輯的參考。

需要注意的是，早期三姿勢 GUI 實驗與後續四影格整合版本可能存在程式版本或時間參數差異。在未逐一核對早期程式及執行紀錄以前，不將上表直接宣稱為早期三姿勢實驗的完整原始執行參數。

#### 4.5.4 GUI 模擬觀察與實驗證據

本專題已保留三姿勢連續動作階段的 GUI 模擬影片紀錄，可作為觀察人形模型上肢姿態變化的視覺證據。

透過 GUI 可以觀察初始姿態、右手臂舉起及右手肘彎曲等階段的姿態呈現，並確認此實驗階段的主要目的為連續動作流程整合。

然而，GUI 影片主要提供姿態變化的視覺觀察證據，不能單獨證明所有模擬步數的角度追蹤誤差均符合特定標準。

本專題在後續四影格實驗中另有記錄部分姿態保持階段的關節角度，但這些數值不得在缺少實驗來源核對的情況下，直接當作早期三姿勢版本的獨立量測結果。

#### 4.5.5 實作成果與限制

三姿勢連續動作的主要成果，在於將右肩膀舉手與右手肘彎曲整合為具有先後順序的姿態控制流程，使本專題由單一關節操作逐步發展為多階段動作控制。

這個階段也為後續加入第四個影格奠定基礎，使控制流程能從彎肘姿態進一步執行伸肘動作，形成簡化的往返控制。

不過，三姿勢動作仍屬於固定基座下的上肢模擬，未涵蓋完整全身協調運動、實體馬達控制或機器人自主平衡功能。

此外，本節主要整理三姿勢控制的設計邏輯與已保留的 GUI 視覺證據，不額外宣稱未經核對的早期關節量測數值。

綜合而言，本專題透過三姿勢連續動作，建立了由初始姿態、舉手至彎肘的基本控制序列，並將此成果延伸為後續四影格簡化揮手往返控制的實作基礎。

### 4.6 四影格簡化揮手往返控制

在三姿勢連續動作的基礎上，本專題進一步加入右手肘重新伸直的動作影格，建立四影格簡化揮手往返控制流程。

本實驗以右肩膀局部 Z 軸舉手及右手肘彎曲、伸直為主要動作，透過 Action Frame、Smoothstep 插值與 PyBullet 關節位置控制，呈現具有指定先後順序的上肢姿態變化。

#### 4.6.1 四影格動作設定

本專題的四個目標姿態如下：

| Frame | 動作名稱 | 右肩膀 Z 軸目標 | 右手肘目標 |
|---|---|---:|---:|
| 01 | Initial Pose | 0° | 0° |
| 02 | Raise Right Arm | 45° | 0° |
| 03 | Wave Right Arm - Bend | 45° | 30° |
| 04 | Wave Right Arm - Extend | 45° | 0° |

Frame 01 用於設定初始姿態。Frame 02 將右肩膀局部 Z 軸目標角度調整至 45°。Frame 03 在維持右肩膀目標姿態的情況下，將右手肘目標角度調整至 30°。Frame 04 則將右手肘目標角度恢復為 0°。

透過 Frame 03 與 Frame 04 的連續執行，可形成簡化的彎肘與伸肘往返動作。然而，此動作僅為人形機器人上肢控制的概念模擬，並非完整人體揮手動作的重現。

#### 4.6.2 四影格連續控制流程

本專題以固定基座方式載入 PyBullet 人形模型，並將右肩膀與右手肘設定為主要控制對象。

控制程式先建立 Frame 01 的初始目標姿態，接著依序執行 Frame 01 至 Frame 02、Frame 02 至 Frame 03，以及 Frame 03 至 Frame 04 的姿態轉換。

每段正式過渡使用 Smoothstep 插值函數，依照模擬進度計算中間目標角度，使控制命令隨步數逐漸變化。

右肩膀為球形關節，須將目標 Euler Angle 轉換為 Quaternion，再交由 PyBullet 多自由度關節控制 API 處理。右手肘為單軸旋轉關節，則以目標角度執行位置控制。

在每段過渡結束後，程式依照 Hold Time 持續施加目標控制命令，並在指定檢查點讀取關節狀態。

### 4.7 16 個邏輯控制欄位的實作與驗證

除了右肩膀及右手肘的連續動作控制之外，本專題亦建立 16 個邏輯控制欄位，作為人形機器人關節控制的軟體映射基礎。

此設計主要用於將容易辨識的動作方向與控制名稱，對應至 PyBullet 人形模型中的 URDF 關節資訊，並透過靜態驗證確認映射資料的一致性。

#### 4.7.1 邏輯控制欄位的設計目的

PyBullet 人形模型以 Joint ID、Joint Name 與 Joint Type 描述關節資訊。然而，直接使用 Joint ID 進行動作設計，對初學者而言較不容易理解各關節的功能及控制方向。

因此，本專題建立 16 個邏輯控制欄位，使用例如 `right_shoulder_z`、`right_elbow` 與 `left_knee` 等名稱，表示希望控制或觀察的關節方向。

其中，球形關節可對應多個邏輯欄位。例如 `right_shoulder_x` 與 `right_shoulder_z` 均對應同一個 `right_shoulder` 關節，只是使用不同的旋轉方向標籤。

這些欄位屬於自行建立的軟體控制抽象介面，不代表模型具有 16 個彼此獨立的活動關節，也不代表配置了 16 顆實體伺服馬達。

#### 4.7.2 邏輯欄位與 URDF 關節映射

本專題使用 `src/humanoid_joint_mapping.py` 管理邏輯欄位與模型關節的對應資料。

各欄位的映射資訊包含邏輯編號、邏輯名稱、Joint ID、Joint Name、Joint Type，以及抽象旋轉方向。

本專題建立的映射結果如下：

| 統計項目 | 數量 |
|---|---:|
| 邏輯控制欄位 | 16 |
| 對應的不同可活動 URDF 關節 | 12 |
| 模型全部 URDF 關節項目（含固定關節） | 15 |
| 模型關節旋轉自由度總和 | 28 |

其中，15 個 URDF 關節項目包含 8 個 Spherical Joint、4 個 Revolute Joint 及 3 個 Fixed Joint。

模型中的可活動關節合計具有 28 個旋轉自由度，但本專題定義的 16 個邏輯控制欄位僅涵蓋部分關節方向，因此兩者不能視為相同數量。

完整的 16 欄位對應表已列於第 2.4 節，後續亦可整理至附錄 B，避免在本節重複呈現相同資料。

#### 4.7.3 靜態映射驗證方法

本專題透過 PyBullet DIRECT 模式載入 `humanoid/humanoid.urdf`，並使用 `getNumJoints()` 與 `getJointInfo()` 查詢模型關節資訊。

驗證工作的主要目的，是確認自行定義的邏輯控制欄位，是否正確對應至模擬模型所提供的關節資料。

依照既有測試紀錄，檢查項目包含：

1. 邏輯控制欄位數量及編號是否符合設定。
2. 各欄位的 Joint ID 是否位於有效範圍。
3. Joint Name 是否與 PyBullet 查詢結果一致。
4. Joint Type 是否與模型關節類型一致。
5. 16 個邏輯控制欄位是否對應至 12 個不同的可活動關節。

此階段屬於靜態映射一致性檢查，不需要透過 GUI 執行關節動作。

#### 4.7.4 靜態驗證結果

依據先前保存的 PowerShell 與 PyBullet 驗證紀錄，16 個邏輯控制欄位均通過靜態映射檢查。

既有測試輸出摘要如下：

```text
Validated Logical Fields: 16
Unique Physical Model Joints: 12
=== Mapping Validation PASS ===
Python Exit Code: 0
```

其中，`Validated Logical Fields: 16` 表示 16 個邏輯欄位已納入驗證，`Unique Physical Model Joints: 12` 表示這些欄位涵蓋 12 個不同的 URDF 可活動關節。

`Mapping Validation PASS` 為驗證程式輸出的整體通過結果；`Python Exit Code: 0` 表示該次程式正常結束。

此項結果支持本專題完成邏輯控制欄位與 URDF 關節資訊之間的靜態一致性檢查。

然而，靜態映射驗證通過，不代表各欄位均已完成實際動作控制、角度追蹤或動態性能驗證。

#### 4.7.5 動態控制範圍與實作限制

本專題目前完成的主要動態控制實驗集中於以下關節：

| 關節名稱 | Joint ID | 動態實驗內容 |
|---|---:|---|
| `right_shoulder` | 3 | 局部 Z 軸 0° 至 45° 抬手控制 |
| `right_elbow` | 4 | 0° 至 30° 再返回 0° 的彎肘與伸肘控制 |

上述兩個關節已整合至 Action Frame 連續動作控制流程，並保留 GUI 模擬影片及指定保持階段的關節角度紀錄。

其餘邏輯控制欄位目前主要完成靜態映射檢查，尚未逐一進行獨立的動態控制測試。

因此，本專題的驗證成果應區分為兩個層級：

第一，完成 16 個邏輯控制欄位與 12 個不同可活動 URDF 關節的靜態映射驗證。

第二，完成右肩膀與右手肘的特定動態控制實驗，包括抬手、彎肘及伸肘往返動作。

綜合而言，本專題透過邏輯控制欄位的建立與靜態一致性驗證，提供一個較容易理解的機器人關節映射介面，並透過部分關節的實際模擬控制展示其應用方向。

此成果可作為未來擴充更多關節動作的基礎，但目前尚不足以宣稱已完成全部 16 個邏輯控制欄位的獨立動態驗證。

## 第六章　問題與改善

### 6.1 關節角度追蹤誤差

在人形機器人動作控制過程中，控制程式所設定的目標角度，不一定與模擬關節在特定時間所呈現的實際角度完全相同。

本專題使用 PyBullet 的位置控制方式，透過 Action Frame 與 Smoothstep 插值逐步更新右肩膀及右手肘的目標姿態，並在部分動作影格完成保持階段後，記錄主要關節的實際角度，作為追蹤結果的初步評估依據。

#### 6.1.1 關節追蹤誤差的定義

本專題使用絕對角度誤差（Absolute Angular Error），表示目標角度與實際角度的差異，其計算公式如下：

\[
e_{\theta}=\left|\theta_{\mathrm{target}}-\theta_{\mathrm{actual}}\right|
\]

其中，\(\theta_{\mathrm{target}}\) 為目標角度，\(\theta_{\mathrm{actual}}\) 為實際量測角度，\(e_{\theta}\) 為絕對角度誤差。

本專題的右肩膀為球形關節，採用特定 Euler Angle 分量進行姿態設定與比較；右手肘則為單軸旋轉關節，可使用單一角度進行比較。

需要注意的是，此處的誤差計算用於本專題指定的角度比較，不能直接視為任意三維旋轉姿態的完整旋轉誤差。

#### 6.1.2 既有關節角度量測結果

依據第四章整理的四影格實驗紀錄，主要關節的 After Hold 量測結果如下：

| 動作階段 | 關節 | 目標角度 | 實際角度 | 絕對誤差 |
|---|---|---:|---:|---:|
| Frame 02 | 右肩膀 Z 軸 | 45° | 44.800512° | 0.199488° |
| Frame 03 | 右手肘 | 30° | 30.000085° | 0.000085° |
| Frame 04 | 右手肘 | 0° | 0.000000° | 0.000000° |

從報告既有的數值可以觀察到，三個指定檢查點的實際角度均接近目標值。

其中，Frame 02 的右肩膀 Z 軸存在 0.199488° 的絕對角度誤差；Frame 03 的右手肘誤差為 0.000085°；Frame 04 的右手肘則記錄為 0.000000°。

上述結果僅代表既有測試紀錄中的指定檢查點，不代表模型在整段動作中的誤差均維持相同水準。

此外，部分相同量測數值亦出現在不同實驗版本的影片證據索引中，其原始執行紀錄及版本歸屬仍須進一步交叉查核。因此，本節不將這些數值解讀為多次獨立實驗的統計結果。

#### 6.1.3 角度誤差的可能影響因素

從位置控制原理來看，關節實際角度與目標值之間可能存在差異，可能的影響因素包括：

1. **位置控制器的動態響應：** 關節需要經過模擬步進，逐步接近所指定的目標姿態。
2. **模擬時間與控制更新：** 控制命令的更新頻率及物理模擬步進方式，可能影響關節在檢查點的姿態。
3. **關節類型與姿態表示：** 右肩膀使用 Quaternion 表示球形關節姿態，角度讀取及 Euler Angle 轉換方式可能影響指定分量的比較結果。
4. **終點保持階段：** Hold Time 使控制器在動作過渡結束後持續施加目標命令，但不保證所有關節的誤差必然降至零。
5. **控制器參數：** 馬達力矩限制及位置控制相關參數可能影響姿態追蹤情形。

上述內容屬於根據模擬控制原理提出的可能原因，並非本專題已透過獨立變因實驗確認的誤差成因。

因此，現階段尚不能判定哪一項因素是右肩膀產生 0.199488° 誤差的主要原因。

#### 6.1.4 Smoothstep 與實際關節追蹤的差異

本專題使用 Smoothstep 產生連續變化的目標角度，使動作影格之間的控制命令不必直接由起始值瞬間切換至終點值。

其主要作用在於改善目標姿態的過渡方式，而不是直接消除 PyBullet 模擬關節的追蹤誤差。

即使 Smoothstep 函數在起點與終點具有零斜率，實際關節仍可能受到控制器響應、模擬條件及其他因素影響，而無法完全符合目標軌跡。

本專題目前僅保留部分保持階段結束後的角度紀錄，尚未提供完整動作期間的逐步目標角度及實際角度序列，因此無法據此分析整段動作的平均追蹤誤差、最大瞬時誤差或時間響應。

#### 6.1.5 改善方向與本節小結

未來若要進一步評估關節控制性能，可在每個模擬步進記錄目標角度、實際角度及時間資訊，建立完整的角度追蹤資料。

在取得完整資料後，可繪製目標角度與實際角度的時間序列曲線，並計算平均絕對誤差及最大絕對誤差，以更全面地評估各階段動作的追蹤情形。

此外，也可在固定其他實驗條件的前提下，分別比較 Hold Time、控制器參數及動作 Duration 對關節追蹤結果的影響。

上述方法屬於後續可採取的改善方向，並非本專題目前已完成的追加實驗。

綜合而言，本專題透過指定保持階段的角度量測，初步確認右肩膀與右手肘的實際姿態接近既定目標值。然而，現有紀錄仍不足以全面評估整段動作的動態追蹤性能，因此後續應以完整時間序列資料及控制參數比較作為主要改善方向。

### 6.2 GUI 視角與動作呈現問題

在人形機器人的三維模擬中，除了正確設定關節目標姿態外，也需要考慮 GUI 攝影機視角、模型初始方向及關節局部座標系對動作觀察的影響。

本專題透過 PyBullet GUI 呈現右肩膀舉手、右手肘彎曲及伸直等動作，並將模擬過程保存為影片。然而，GUI 畫面所呈現的外觀變化，並不能直接等同於關節的實際角度或控制精度。

#### 6.2.1 三維模型與觀察視角的關係

PyBullet GUI 以三維場景呈現人形機器人模型。觀察者可以透過攝影機視角查看模型的姿態與動作，但同一個關節旋轉動作，在不同視角下可能呈現不同的外觀。

例如，從模型正面觀察右手臂的旋轉，與從側面觀察相同動作，可能得到不同的視覺印象。

因此，觀察者需要區分關節實際設定的旋轉方向與 GUI 畫面中的視覺方向，避免直接以螢幕上手臂的移動方向推斷關節局部旋轉軸。

#### 6.2.2 關節局部座標與模型初始方向

本專題右肩膀的目標姿態使用 Euler Angle 描述，並以局部 Z 軸由 0° 轉換至 +45°，作為抬手動作的主要控制設定。

然而，局部 Z 軸的正向旋轉，並不代表模型手臂在世界座標系中必然沿垂直方向移動。

模型的初始方向、關節座標配置及攝影機位置，均可能影響 GUI 中所觀察到的姿態。

因此，正式說明實驗成果時，本專題以「右肩膀局部 Z 軸目標旋轉 +45°」描述控制設定，而不直接將其解釋為手臂相對地面抬高 45°。

此外，模型基座位置及初始方向應以實際 Python 載入程式為準，避免未經原始碼核對的數值影響後續座標系統分析。

#### 6.2.3 動作呈現與影片觀察的限制

本專題已透過 PyBullet GUI 保存三類主要實驗的影片索引，包括右肩膀 Z 軸舉手、三姿勢連續動作及四影格簡化揮手往返控制。

影片可用於觀察不同動作階段的姿態變化，以及右肩膀與右手肘控制動作的執行順序。

然而，從 GUI 影片無法單獨確認每個模擬步進所對應的精確關節角度，也無法直接判斷動作是否符合特定的速度或加速度要求。

攝影機視角及模型遮擋亦可能影響部分關節姿態的辨識，因此，若僅根據單一視角進行觀察，可能無法完整理解三維關節的旋轉情形。

目前本專題尚未針對不同攝影機視角執行正式的量化比較，因此上述內容屬於三維模擬結果呈現時需要注意的觀察限制，而非已獨立量測確認的 GUI 故障或顯示異常。

#### 6.2.4 GUI 動作呈現的改善方向

未來若希望提高模擬影片的可讀性及成果展示效果，可考慮以下改善方式：

1. **統一攝影機視角：** 在相同觀察方向下錄製不同版本的控制動作，方便比較姿態變化。
2. **增加正面與側面觀察：** 透過不同視角輔助判斷肩膀及手肘的三維旋轉情形。
3. **顯示目前 Action Frame：** 在模擬畫面或同步紀錄中標示正在執行的動作階段。
4. **補充目標角度資訊：** 將目前目標角度與關節狀態紀錄對應，協助區分控制命令及實際姿態。
5. **建立一致的影片歸檔方式：** 將攝影機設定、執行程式版本及影片檔名納入證據索引，以提高可追溯性。

上述項目屬於後續可進行的改善方向，不代表本專題目前已完成全部功能或相關視角比較測試。

#### 6.2.5 本節小結

本專題透過 PyBullet GUI，將原本以數值表示的關節角度與 Action Frame 目標設定，轉換為可供觀察的人形機器人姿態變化。

GUI 模擬有助於理解右肩膀舉手、右手肘彎曲與伸直之間的動作關係，但其視覺呈現仍受到攝影機視角、模型方向及關節局部座標系等因素影響。

因此，GUI 影片適合作為動作外觀與執行順序的視覺證據，而關節控制精度仍應以對應的程式輸出及測試紀錄為主要依據。

綜合而言，本專題已建立基本的人形機器人 GUI 動作呈現方式，後續可透過統一視角、增加輔助資訊及改善影片索引，提高實驗成果的可讀性與可驗證性。

#### 6.4.4 模型條件與 GUI 驗證的限制

此設定降低了整體機身位移對觀察的干擾，但無法代表自由基座人形機器人在實際站立或動作時的平衡情形。

未來可統一 GUI 攝影機位置、補充正面與側面視角，並同步記錄控制程式版本與關節狀態，使影片與數值紀錄具有更明確的對應關係。

至於自由基座平衡與步行控制，涉及本專題尚未建立的控制條件，應視為獨立的後續研究方向，而不是本次實作已完成的功能。

#### 7.2.4 模擬步進與時間換算結果

本專題使用 240 Hz 作為模擬步進基準，其模擬時間間隔為：

\[
\Delta t=\frac{1}{240}\text{ s}
\]

若動作持續時間為 \(T\) 秒，則對應的理論模擬步數為：

\[
N=T\times240
\]

依照既有動作時間參數，可得到下列換算結果：

| 動作過渡 | Duration 對應步數 | Hold Time 對應步數 | 合計步數 |
|---|---:|---:|---:|
| Frame 01 → 02 | 480 | 120 | 600 |
| Frame 02 → 03 | 240 | 72 | 312 |
| Frame 03 → 04 | 240 | 72 | 312 |
| **合計** | **960** | **264** | **1,224** |

上述數值係依據設定時間與 240 Hz 模擬頻率計算而得，用於說明控制參數與理論模擬步數之間的對應關係。

其中：

\[
N_{\mathrm{total}}=5.1\times240=1224
\]

此處的 1,224 步為名義模擬步數換算結果，不代表本專題已另行取得完整的逐步執行日誌，也不包含初始化或其他可能存在的額外步進。

因此，本節僅將其作為時間設定的計算驗證，不視為實際影片影格數或獨立量測得到的程式執行次數。

#### 7.2.5 Smoothstep 對目標角度的影響

本專題使用 Smoothstep 函數產生動作過渡期間的目標角度，其計算方式為：

\[
s(u)=3u^2-2u^3
\]

其中，\(u\) 表示 0 至 1 之間的正規化動作進度。

目標角度的插值公式為：

\[
\theta(u)=\theta_0+(\theta_1-\theta_0)s(u)
\]

以右手肘從 0° 彎曲至 30° 為例，可計算不同動作進度對應的目標角度：

| 動作進度 | Smoothstep 比例 | 目標角度 |
|---|---:|---:|
| 0% | 0.00000 | 0.0000° |
| 25% | 0.15625 | 4.6875° |
| 50% | 0.50000 | 15.0000° |
| 75% | 0.84375 | 25.3125° |
| 100% | 1.00000 | 30.0000° |

這些數值反映 Smoothstep 所產生的目標角度變化，並非 PyBullet 實際關節在對應時間點的量測角度。

因此，Smoothstep 可以用於建立連續的目標姿態過渡，但不能只根據插值計算結果，就宣稱實際關節在所有模擬步進中均完全符合目標軌跡。

#### 7.2.6 測試結果綜合討論

綜合本專題已整理的關節與時間控制測試資料，可歸納出以下結果：

1. **目標姿態設定：** 已建立右肩膀局部 Z 軸 0° 至 45°，以及右手肘 0° 至 30° 再返回 0° 的動作目標。
2. **關節控制驗證：** 已保存三筆主要指定檢查點的角度量測摘要，顯示相關關節在檢查點接近目標姿態。
3. **時間參數整合：** 四影格正式過渡與保持時間設定合計 5.1 秒，並可依 240 Hz 推算名義模擬步數。
4. **插值方法應用：** 已使用 Smoothstep 產生逐步變化的目標姿態，作為不同動作影格之間的過渡方式。
5. **GUI 視覺紀錄：** 已建立主要實驗影片的證據索引，用於說明各階段動作的視覺呈現。

上述成果支持本專題已建立基本的動作影格控制、模擬時間管理及部分關節角度檢查流程。

不過，目前仍缺乏完整的目標角度與實際角度時間序列，因此無法進一步評估整段動作的平均絕對誤差、最大瞬時誤差或追蹤延遲。

此外，本專題並未進行不同控制器參數或不同插值方法的正式比較實驗，因此也不能據此判定 Smoothstep 相較其他方法具有全面性的控制性能優勢。

綜合而言，本專題已完成固定基座 PyBullet 人形模型的基本關節與時間控制模擬，並保留部分結果作為初步驗證資料。後續若需要更完整的控制性能評估，應先建立逐步關節狀態紀錄及確認原始測試資料來源，再進行進一步的分析與比較。

### 7.3 學習心得與技術收穫

本專題透過 Python 與 PyBullet，將人形機器人關節結構、姿態表示、動作影格設計與時間控制等基礎概念，轉換為可實際執行及觀察的軟體模擬流程。

在專題實作過程中，主要的技術學習不僅是使虛擬人形模型完成特定動作，也包括理解關節資料的組成方式、控制命令與實際關節狀態的差異，以及如何使用程式輸出和影片建立可追溯的實驗紀錄。

本節依照本專題的實作內容，整理主要學習心得與技術收穫。

#### 7.3.1 對人形機器人關節結構與自由度的理解

透過 PyBullet 載入 `humanoid/humanoid.urdf`，本專題實際接觸 URDF 模型的 Joint ID、Joint Name 與 Joint Type 等資料，進一步理解不同關節類型對控制方式的影響。

在關節結構分析中，本專題確認模型具有 15 個 URDF 關節項目，其中包含 8 個球形關節、4 個旋轉關節及 3 個固定關節，合計具有 28 個關節旋轉自由度。

透過建立 16 個邏輯控制欄位，也進一步理解軟體控制名稱、實際 URDF 關節及旋轉自由度之間的差異。

例如，`right_shoulder_x` 與 `right_shoulder_z` 雖然屬於不同的邏輯欄位，但都對應同一個 `right_shoulder` 球形關節。

因此，本專題的重要學習收穫之一，是理解關節數量、自由度及控制欄位數量不能直接畫上等號。

此外，透過 PyBullet DIRECT 模式進行靜態映射檢查，也建立了使用程式確認關節資訊一致性的基本方法，而不只是依照關節名稱推測模型結構。

#### 7.3.2 Euler Angle 與 Quaternion 的實作應用

在三維關節姿態控制方面，本專題使用 Euler Angle 定義右肩膀的目標姿態，並透過 `getQuaternionFromEuler()` 將其轉換為 Quaternion，作為 PyBullet 球形關節控制器的目標輸入。

透過這個實作流程，可以理解 Euler Angle 與 Quaternion 在控制系統中扮演不同角色。

Euler Angle 適合用來描述較容易閱讀的目標角度設定，而 Quaternion 則適合提供三維旋轉姿態的資料表示。

本專題也透過實際控制設定，理解右肩膀局部 Z 軸旋轉 +45°，不代表手臂相對地面或世界座標系的絕對抬升角度為 45°。

這項區分顯示，在分析人形機器人的三維姿態時，必須同時考慮關節局部座標系、模型基座方向及觀察視角，才能避免對動作方向產生錯誤解讀。

#### 7.3.3 Action Frame 與 Smoothstep 動作控制的學習

本專題使用 Action Frame 將簡化的右手臂動作拆分為初始姿態、抬手、彎肘及伸肘四個階段，並由控制程式依序執行。

透過這種設計，可以理解動作資料與控制流程分離的優點。

動作資料負責定義關節目標角度及時間參數；控制程式則負責讀取資料、產生中間目標姿態，以及向 PyBullet 關節控制器傳送命令。

在動作過渡方面，本專題使用 Smoothstep 插值函數：

\[
s(u)=3u^2-2u^3
\]

依據正規化動作進度，逐步產生不同影格之間的目標角度。

透過此項實作，可以理解插值函數主要處理的是目標命令如何隨時間變化，而不是直接保證實際關節能完全追蹤每個目標值。

此外，本專題亦區分 Duration 與 Hold Time，並以 240 Hz 為模擬步進基準，將時間設定轉換為相應的理論模擬步數。

這些實作建立了對動作順序、角度過渡及時間參數之間關係的基本理解。

#### 7.3.4 從目標角度到實際角度的驗證觀念

在初步學習關節控制時，設定目標角度容易被理解為關節已經到達指定位置。

然而，透過本專題的 After Hold 量測紀錄，可以進一步區分控制器所接收的目標姿態與模擬關節實際呈現的姿態。

例如，在既有四影格測試摘要中，Frame 02 的右肩膀局部 Z 軸目標角度為 45°，而指定保持階段結束後的實際角度記錄為 44.800512°，兩者存在 0.199488° 的絕對誤差。

這項結果說明，即使控制命令已經設定為特定目標，實際關節仍可能存在些微差異。

因此，關節控制的驗證不能只檢查程式是否設定了正確角度，也需要讀取關節狀態並進行比較。

本專題目前保存的是部分指定檢查點數值，尚不足以分析整段動作的追蹤性能。這也使本專題在實作過程中建立了區分「已設定」、「已執行」與「已量測驗證」三種狀態的重要觀念。

#### 7.3.5 程式版本與實驗證據管理的收穫

除了動作控制技術外，本專題也透過不同實作階段的資料整理，理解程式版本與實驗證據管理的重要性。

本專題由早期右肩膀舉手模擬，逐步發展至三姿勢連續動作，再擴充為四影格簡化揮手往返控制。

在此過程中，部分控制程式雖然保留原有檔名，但其實際功能已隨實驗階段調整。

例如，`src/humanoid_three_frame_gui.py` 的名稱仍保留三影格階段的命名，但後續已擴充為四影格控制版本。

研究過程以固定基座的 `humanoid/humanoid.urdf` 模型為對象，依序完成模擬環境建置、URDF 關節資訊分析、邏輯控制欄位映射、Action Frame 動作設計、Smoothstep 插值及 GUI 連續動作模擬，並整理指定關節角度測試結果與影片證據索引。

#### 8.1.1 完成人形機器人關節結構與控制欄位的基本分析

本專題透過 PyBullet 查詢 `humanoid/humanoid.urdf` 的關節資訊，依據既有驗證紀錄整理出 15 個 URDF 關節項目，其中包含 8 個球形關節、4 個旋轉關節及 3 個固定關節，合計具有 28 個關節旋轉自由度。

在此基礎上，本專題自行建立 16 個邏輯控制欄位，對應至 12 個不同的可活動 URDF 關節，並使用 DIRECT 模式完成 Joint ID、Joint Name 及 Joint Type 等靜態一致性檢查。

上述成果顯示，本專題已建立基本的關節資料查詢及軟體映射流程，有助於理解機器人關節結構、自由度與控制介面之間的關係。

然而，靜態映射驗證的通過結果不代表全部 16 個邏輯欄位均已完成動態控制測試，也不代表模型配置了 16 顆實體伺服馬達。

#### 8.1.2 建立四影格簡化上肢動作控制流程

本專題以右肩膀與右手肘為主要動態控制對象，透過 Action Frame 建立初始姿態、抬手、彎肘與伸肘四個目標姿態。

其中，右肩膀局部 Z 軸目標角度由 0° 調整至 45°，右手肘則依序由 0° 彎曲至 30°，再返回 0°。

本專題透過 Euler Angle 與 Quaternion 的姿態轉換設定右肩膀球形關節，並使用 PyBullet 單軸位置控制方式設定右手肘目標角度。

在不同動作影格之間，控制程式使用 Smoothstep 插值產生逐步變化的目標姿態，使動作控制命令按照預定順序與時間參數執行。

四影格版本的三段正式動作過渡合計具有 4.0 秒 Duration 及 1.1 秒 Hold Time，總計為 5.1 秒的名義模擬時間。依照 240 Hz 的模擬步進基準，可換算為 1,224 個名義模擬步數。

需要注意的是，5.1 秒及 1,224 步是根據控制設定計算的結果，不等於實際影片長度，也不能直接視為獨立量測得到的完整執行時間紀錄。

此外，第四個影格僅將右手肘重新伸直，右肩膀仍維持 45° 目標設定，因此本專題完成的是簡化的彎肘與伸肘往返控制，而不是完整返回初始姿態的全手臂運動。

#### 8.1.3 取得指定檢查點的關節角度驗證結果

本專題在部分動作影格完成保持階段後，保存主要關節的目標角度及實際角度紀錄，並以絕對角度誤差進行比較。

依據既有四影格測試摘要，Frame 02 的右肩膀局部 Z 軸目標為 45°，實際記錄為 44.800512°，絕對誤差為 0.199488°。

Frame 03 的右手肘目標為 30°，實際記錄為 30.000085°，絕對誤差為 0.000085°。

Frame 04 的右手肘目標為 0°，實際記錄為 0.000000°，絕對誤差為 0.000000°。

上述結果顯示，在報告既有紀錄的指定檢查點，相關關節的實際角度接近預定目標值，可作為基本位置控制結果的初步驗證資料。

#### 8.2.2 建立完整關節角度時間序列

本專題目前主要保存部分 Action Frame 在保持階段結束後的目標角度與實際角度紀錄。

雖然這些數值可用於初步確認特定檢查點的控制結果，但仍不足以分析整段動作過程中的動態追蹤性能。

對於右肩膀球形關節，未來若要分析任意三維姿態的追蹤差異，則應進一步採用適當的三維旋轉誤差表示方式，而不僅比較單一 Euler Angle 分量。

此方向可使關節控制分析從少數檢查點逐步發展為完整動態軌跡評估。

#### 8.2.3 比較不同動作插值與時間控制方法

本專題目前使用 Smoothstep 產生不同動作影格之間的目標姿態，並透過 Duration 與 Hold Time 管理模擬動作時間。

此方式已可應用於本專題的簡化上肢動作控制，但尚未針對其他插值方法或不同控制參數進行正式比較。

比較過程應維持相同的模型、初始姿態、目標角度、模擬步進及其他控制條件，避免因實驗條件不同而產生無法合理解釋的結果。

#### 8.2.4 擴充多關節協調動作與機器人運動學

### A.2 邏輯控制欄位程式

`humanoid_joint_mapping.py` 使用 `LOGICAL_JOINT_MAPPING` 清單儲存 16 個邏輯控制欄位。

每筆映射資料包含邏輯編號、欄位名稱、URDF Joint ID、Joint Name、關節類型及抽象旋轉方向。

例如：

```python
{
    "id": 4,
    "name": "right_shoulder_z",
    "joint_id": 3,
    "joint_name": "right_shoulder",
    "type": "SPHERICAL",
    "axis": "Z"
}
```

上述資料表示邏輯欄位 `right_shoulder_z` 對應 URDF Joint ID 3 的球形關節 `right_shoulder`，並使用 Z 作為抽象旋轉方向標籤。

程式亦提供 `get_logical_joint(name)` 函式，用於根據邏輯欄位名稱查詢對應資料。當指定的名稱不存在時，函式會產生 `ValueError`。

本程式屬於映射資料定義與查詢工具，不直接向 PyBullet 傳送馬達控制命令。

### A.3 Action Frame 動作資料程式

`humanoid_action_frames.py` 使用 `ACTION_FRAMES` 清單定義四個動作影格。

各影格包含 `frame_id`、`name`、`duration`、`hold` 及 `joints` 等主要資料鍵值。

右肩膀的目標姿態由 `euler_deg` 記錄，右手肘則使用 `angle_deg` 記錄單軸目標角度。

例如，Frame 03 定義如下：

```python
{
    "frame_id": 3,
    "name": "Wave Right Arm - Bend",
    "duration": 1.0,
    "hold": 0.3,
    "joints": {
        "right_shoulder": {
            "joint_id": 3,
            "type": "SPHERICAL",
            "euler_deg": [0.0, 0.0, 45.0]
        },
        "right_elbow": {
            "joint_id": 4,
            "type": "REVOLUTE",
            "angle_deg": 30.0
        }
    }
}
```

此影格表示右肩膀局部 Z 軸目標維持 45°，右手肘目標為 30°，對應名義 Duration 1.0 秒及 Hold Time 0.3 秒。

程式提供 `get_action_frame(frame_id)` 函式，供 GUI 控制程式根據影格編號讀取資料。

此檔案只負責資料定義及查詢，並不直接執行 PyBullet GUI 或物理模擬。

### A.4 右肩膀舉手 GUI 控制程式

`humanoid_action_frame_gui.py` 用於執行 Frame 01 至 Frame 02 的關節控制。

本程式以 PyBullet GUI 載入固定基座人形模型，使用 240 Hz 作為模擬步進基準。

主要設定包括：

```python
FPS = 240
RIGHT_SHOULDER = 3
RIGHT_ELBOW = 4
SHOULDER_FORCE = [100.0, 100.0, 100.0]
```

模型初始化時，程式使用以下設定：

```python
orientation = p.getQuaternionFromEuler(
    [math.pi / 2, 0, 0]
)

robot = p.loadURDF(
    "humanoid/humanoid.urdf",
    basePosition=[0, 0, 4.0],
    baseOrientation=orientation,
    useFixedBase=True
)
```

在完成初始姿態設定後，程式讀取 Frame 01 與 Frame 02 的目標角度，透過 Smoothstep 計算中間目標值。

右肩膀使用 `setJointMotorControlMultiDof()` 輸入 Quaternion 目標姿態，右手肘則使用 `setJointMotorControl2()` 設定單軸目標角度。

程式也提供 `measure()` 函式，可在指定檢查點讀取右肩膀與右手肘的實際角度，並輸出目標值、實際值及絕對誤差。

在此版本中，主要過渡為 Frame 01 至 Frame 02，不包含後續彎肘與伸肘的完整四影格控制。

### A.5 四影格連續 GUI 控制程式

`humanoid_three_frame_gui.py` 為本專題目前使用的四影格 GUI 控制版本。

雖然檔名仍保留 `three_frame`，但實際程式已載入 Frame 01、Frame 02、Frame 03 與 Frame 04，並依序執行三段正式姿態轉換。

程式使用 `move_between_frames(start_frame, end_frame)` 函式，讀取前後影格的目標角度與時間參數。

其主要流程如下：

```python
move_between_frames(frame_01, frame_02)
move_between_frames(frame_02, frame_03)
move_between_frames(frame_03, frame_04)
```

各段過渡先計算所需模擬步數：

```python
steps = round(duration * FPS)
hold_steps = round(hold_duration * FPS)
```

再透過 Smoothstep 產生中間目標姿態：

```python
u = (i + 1) / steps
s = smoothstep(u)
```

右肩膀與右手肘均依照起始與目標角度，套用插值比例產生當前控制命令。

程式執行每個模擬步進後，於指定位置讀取關節狀態；每段過渡結束時分別輸出 Before Hold 與 After Hold 的量測資訊。

此版本的三段正式動作 Duration 合計為 4.0 秒，Hold Time 合計為 1.1 秒，總計 5.1 秒的名義模擬時間。

依據 240 Hz 的設定，可換算為 1,224 個名義模擬步數，不包含初始化及其他額外處理時間。

需要注意的是，此程式最上方的說明文字仍保留早期 `Frame 01 -> Frame 02` 的內容，但實際主程式已執行四影格控制。正式使用時，應依主程式的實際呼叫流程判斷功能，不應只根據檔名或文件說明推論動作階段。

### A.6 關節量測與誤差計算

兩支 GUI 控制程式均提供關節量測流程。

shoulder_error = abs(

elbow_error = abs(

上述方法適用於本專題指定旋轉方向的角度比較，但不等同於任意三維旋轉姿態的完整旋轉距離計算。

#### B.2 邏輯欄位與模型關節數量統計

本專題的邏輯映射具有以下數量關係：

| 統計項目 | 數量 |
|---|---:|
| 邏輯控制欄位 | 16 |
| 對應的不同可活動 URDF 關節 | 12 |
| 模型全部 URDF 關節項目 | 15 |
| Spherical Joint | 8 |
| Revolute Joint | 4 |
| Fixed Joint | 3 |
| 模型關節旋轉自由度總和 | 28 |

其中，16 個邏輯欄位對應至 12 個不同的可活動關節，是因為部分球形關節具有不只一個邏輯控制方向。

例如，`right_shoulder_x` 與 `right_shoulder_z` 均對應 Joint ID 3 的 `right_shoulder`。兩個欄位代表同一個球形關節的不同抽象方向，而非兩個獨立的 URDF 關節。

另外，28 個旋轉自由度是根據模型的 8 個球形關節與 4 個單軸旋轉關節計算而得：

\[
DOF=8\times3+4\times1=28
\]

因此，邏輯欄位數量、URDF 關節數量及關節旋轉自由度應分別理解，不能直接視為相同概念。

#### B.3 邏輯控制欄位的資料結構

`humanoid_joint_mapping.py` 使用 `LOGICAL_JOINT_MAPPING` 清單儲存映射資料。

每筆資料包含以下欄位：

| 資料鍵值 | 說明 |
|---|---|
| `id` | 邏輯控制欄位編號 |
| `name` | 邏輯控制欄位名稱 |
| `joint_id` | 對應 URDF Joint ID |
| `joint_name` | 對應 URDF Joint Name |
| `type` | 關節類型 |
| `axis` | 本專題定義的抽象旋轉方向 |

以右肩膀 Z 軸欄位為例：

```python
{
    "id": 4,
    "name": "right_shoulder_z",
    "joint_id": 3,
    "joint_name": "right_shoulder",
    "type": "SPHERICAL",
    "axis": "Z"
}
```

程式提供 `get_logical_joint(name)` 函式，供其他程式根據名稱查詢對應的映射資料。

例如：

```python
joint_info = get_logical_joint("right_shoulder_z")
print(joint_info)
```

上述查詢會取得 `right_shoulder_z` 在映射清單中的資料；若名稱不存在，則會產生 `ValueError`。

需要注意的是，本函式僅查詢事先定義的 Python 資料，不會因此自動載入 PyBullet 模型、檢查實際關節狀態或執行馬達控制。

#### C.4 Duration、Hold Time 與模擬步數換算

本專題使用 240 Hz 作為模擬步進基準，對應的模擬時間間隔為：

\[
\Delta t=\frac{1}{240}\text{ s}
\]

四影格版本的正式動作過渡如下：

| 動作過渡 | Duration | Hold Time | 名義時間合計 |
|---|---:|---:|---:|
| Frame 01 → 02 | 2.0 s | 0.5 s | 2.5 s |
| Frame 02 → 03 | 1.0 s | 0.3 s | 1.3 s |
| Frame 03 → 04 | 1.0 s | 0.3 s | 1.3 s |
| **合計** | **4.0 s** | **1.1 s** | **5.1 s** |

程式採用 `round(duration * FPS)` 及 `round(hold_duration * FPS)`，計算各段正式動作所使用的步數。

依據既有時間設定，可換算如下：

| 動作過渡 | 過渡步數 | 保持步數 | 合計步數 |
|---|---:|---:|---:|
| Frame 01 → 02 | 480 | 120 | 600 |
| Frame 02 → 03 | 240 | 72 | 312 |
| Frame 03 → 04 | 240 | 72 | 312 |
| **合計** | **960** | **264** | **1,224** |

計算方式為：

\[
N=T\times FPS
\]

因此：

\[
N_{\mathrm{total}}=5.1\times240=1224
\]

上述 5.1 秒及 1,224 個步數，係由既有控制設定換算而得，屬於三段正式過渡及保持階段的名義模擬時間與步數。

Frame 01 的資料雖包含 Duration 2.0 秒與 Hold Time 0.5 秒，但四影格 GUI 程式主要將該影格用於初始化，不將其資料欄位直接計入正式過渡。

此外，名義模擬時間不等於實際影片長度、Windows 系統的牆上時鐘時間，也不代表本專題已獨立保存 1,224 筆逐步量測紀錄。

#### C.5 Smoothstep 目標角度與實際量測的區分

本專題使用 Smoothstep 計算動作過渡期間的目標姿態：

\[
s(u)=3u^2-2u^3
\]

其中，\(u\) 為介於 0 至 1 之間的正規化進度。

角度插值為：

\[
\theta(u)=\theta_0+(\theta_1-\theta_0)s(u)
\]

以右手肘由 0° 彎曲至 30° 為例，可得到以下目標角度：

| 動作進度 | Smoothstep 比例 | 理論目標角度 |
|---|---:|---:|
| 0% | 0.00000 | 0.0000° |
| 25% | 0.15625 | 4.6875° |
| 50% | 0.50000 | 15.0000° |
| 75% | 0.84375 | 25.3125° |
| 100% | 1.00000 | 30.0000° |

上述數值是插值公式所產生的理論目標角度，不是使用 `getJointState()` 從 PyBullet 取得的實際量測值。

實際關節角度仍可能受到位置控制器、模擬步進及關節動態條件影響。

因此，未來若需分析完整追蹤誤差，必須在各模擬步進同步保存目標角度與實際角度，不能將理論插值表當作實際控制結果。

目前提供的 `humanoid_three_frame_gui.py` 已包含四個 Action Frames，因此不能僅根據目前原始碼，就認定 V10 早期三姿勢影片與 V11 四影格影片使用完全相同的程式內容或控制參數。

#### D.3 各影片主要觀察內容

本專題的三支影片分別對應不同的模擬觀察目的。

**V09：右肩膀 Z 軸舉手**

V09 對應右肩膀球形關節的舉手控制階段，主要用於觀察模型右手臂由初始姿態轉向指定舉手目標姿態的視覺變化。

其控制概念涉及右肩膀局部 Z 軸 0° 至 45° 的目標姿態設定。

**V10：三姿勢連續控制**

V10 對應三姿勢控制階段，包含初始姿態、右肩膀舉手及右手肘彎曲的動作設計。

主要觀察重點為控制流程如何從單一關節舉手，發展為右肩膀及右手肘依序執行的多階段姿態控制。

**V11：四影格簡化揮手往返**

V11 對應四影格整合版本，主要觀察初始姿態、舉手、彎肘及伸肘的連續控制順序。

其中，Frame 04 的右手肘目標角度由 30° 返回 0°，而右肩膀局部 Z 軸仍保持 45° 目標姿態，因此影片所對應的動作應描述為簡化彎肘與伸肘往返，而非整隻手臂恢復初始姿態。
